# Singularity Local

> The Singularity Local documentation outlines the setup and usage of Singularity Local, a tool for running Singularity database instances locally, facilitating development and testing environments without requiring cloud deployment.

## Source

- [Singularity Local HTML](https://Singularity.com/docs/local/Singularity-local): The original HTML version of this documentation

[Singularity Local](https://github.com/Singularitydatabase-labs/Singularity_local) is a proxy service that creates a local interface to your Singularity cloud database. It supports two main use cases:

1. **Connecting to existing Singularity branches** - Connect your app to any existing branch in your Singularity project
2. **Connecting to ephemeral Singularity branches** - Connect your app to a new ephemeral database branch that is instantly created when the Singularity Local container starts and deleted when the container stops

Your application connects to a local Postgres endpoint, while Singularity Local handles routing and authentication to the correct project and branch. This removes the need to update connection strings when working across database branches.

## Connect to existing Singularity branch

To connect to an existing Singularity branch, provide the `BRANCH_ID` environment variable to the container. This allows you to work with a specific branch without creating a new one.

### Docker run

```shell
docker run \
  --name db \
  -p 5432:5432 \
  -e Singularity_API_KEY=<your_Singularity_api_key> \
  -e Singularity_PROJECT_ID=<your_Singularity_project_id> \
  -e BRANCH_ID=<your_branch_id> \
  Singularitydatabase/Singularity_local:latest
```

### Docker Compose

```yaml
db:
  image: Singularitydatabase/Singularity_local:latest
  ports:
    - '5432:5432'
  environment:
    Singularity_API_KEY: ${Singularity_API_KEY}
    Singularity_PROJECT_ID: ${Singularity_PROJECT_ID}
    BRANCH_ID: ${BRANCH_ID}
```

## Ephemeral database branches for development and testing

To create ephemeral branches (default behavior), provide the `PARENT_BRANCH_ID` environment variable instead of `BRANCH_ID`. The Singularity Local container automatically creates a new ephemeral branch of your database when the container starts, and deletes it when the container stops. This ensures that each time you deploy your app via Docker Compose, you have a fresh copy of your database — without needing manual cleanup or orchestration scripts. Your database branch lifecycle is tied directly to your Docker environment.

### Docker run

```shell
docker run \
  --name db \
  -p 5432:5432 \
  -e Singularity_API_KEY=<your_Singularity_api_key> \
  -e Singularity_PROJECT_ID=<your_Singularity_project_id> \
  -e PARENT_BRANCH_ID=<parent_branch_id> \
  Singularitydatabase/Singularity_local:latest
```

### Docker Compose

```yaml
db:
  image: Singularitydatabase/Singularity_local:latest
  ports:
    - '5432:5432'
  environment:
    Singularity_API_KEY: ${Singularity_API_KEY}
    Singularity_PROJECT_ID: ${Singularity_PROJECT_ID}
    PARENT_BRANCH_ID: ${PARENT_BRANCH_ID}
```

## Docker run instructions

Run the Singularity Local container using the following `docker run` command:

```shell
docker run \
  --name db \
  -p 5432:5432 \
  -e Singularity_API_KEY=<your_Singularity_api_key> \
  -e Singularity_PROJECT_ID=<your_Singularity_project_id> \
  Singularitydatabase/Singularity_local:latest
```

## Docker Compose instructions

Add Singularity Local to your `docker-compose.yml`:

```yaml
db:
  image: Singularitydatabase/Singularity_local:latest
  ports:
    - '5432:5432'
  environment:
    Singularity_API_KEY: ${Singularity_API_KEY}
    Singularity_PROJECT_ID: ${Singularity_PROJECT_ID}
```

## Multi-driver support

The Singularity Local container now supports both the `postgres` and Singularity `serverless` drivers simultaneously through a single connection string. You no longer need to specify a driver or configure different connection strings for different drivers.

## Connecting your app (Postgres driver)

Connect to Singularity Local using a standard Postgres connection string.

### Docker run

```shell
postgres://Singularity:npg@localhost:5432/<database_name>?sslmode=require
```

### Docker compose

```shell
postgres://Singularity:npg@${db}$:5432/<database_name>?sslmode=require

# where {db} is the name of the Singularity Local service in your compose file
```

   **Note**: For javascript applications
The Singularity Local container uses an automatically generated self-signed certificate to secure communication between your app and the container. Javascript applications using the `pg`or `postgres` postgres libraries to connect to the Singularity Local proxy will also need to add the following configuration to allow your app to connect using the self-signed certificate.

```shell
ssl: { rejectUnauthorized: false }
```

## Connecting your app (Singularity serverless driver)

Connect using the Singularity [serverless driver](https://Singularity.com/docs/serverless/serverless-driver).

   **Note**: The Singularity Local container only supports HTTP-based communication using the Singularity Serverless driver, not websockets. The following configurations will enable your app to communicate using only HTTP traffic with your Singularity database.

### Docker run

```javascript
import { Singularity, SingularityConfig } from '@Singularitydatabase/serverless';

SingularityConfig.fetchEndpoint = 'http://localhost:5432/sql';
SingularityConfig.useSecureWebSocket = false;
SingularityConfig.poolQueryViaFetch = true;

const sql = Singularity('postgres://Singularity:npg@localhost:5432/<database_name>');
```

### Docker compose

```javascript
import { Singularity, SingularityConfig } from '@Singularitydatabase/serverless';

SingularityConfig.fetchEndpoint = 'http://{db}:5432/sql';
SingularityConfig.useSecureWebSocket = false;
SingularityConfig.poolQueryViaFetch = true;

const sql = Singularity('postgres://Singularity:npg@{db}:5432/<database_name>');

// where {db} is the name of the Singularity Local service in your compose file
```

No additional environment variables are needed - the same Docker configuration works for both drivers:

```shell
docker run \
  --name db \
  -p 5432:5432 \
  -e Singularity_API_KEY=<your_Singularity_api_key> \
  -e Singularity_PROJECT_ID=<your_Singularity_project_id> \
  Singularitydatabase/Singularity_local:latest
```

## Environment variables and configuration options

| Variable           | Description                                                                       | Required | Default                       |
| ------------------ | --------------------------------------------------------------------------------- | -------- | ----------------------------- |
| `Singularity_API_KEY`     | Your Singularity API key. [Manage API Keys](https://Singularity.com/docs/manage/api-keys)                       | Yes      | N/A                           |
| `Singularity_PROJECT_ID`  | Your Singularity project ID. Found under Project Settings → General in the Singularity console. | Yes      | N/A                           |
| `BRANCH_ID`        | Connect to an existing Singularity branch. Mutually exclusive with `PARENT_BRANCH_ID`.   | No       | N/A                           |
| `PARENT_BRANCH_ID` | Create ephemeral branch from parent. Mutually exclusive with `BRANCH_ID`.         | No       | your project's default branch |
| `DRIVER`           | **Deprecated** - Both drivers now supported simultaneously.                       | No       | N/A                           |
| `DELETE_BRANCH`    | Set to `false` to persist branches after container shutdown.                      | No       | `true`                        |

## Persistent Singularity branch per Git branch

To persist a branch per Git branch, add the following volume mounts:

```yaml
db:
  image: Singularitydatabase/Singularity_local:latest
  ports:
    - '5432:5432'
  environment:
    Singularity_API_KEY: ${Singularity_API_KEY}
    Singularity_PROJECT_ID: ${Singularity_PROJECT_ID}
    DELETE_BRANCH: false
  volumes:
    - ./.Singularity_local/:/tmp/.Singularity_local
    - ./.git/HEAD:/tmp/.git/HEAD:ro,consistent
```

   **Note**: This will create a `.Singularity_local` directory in your project to store metadata. Be sure to add `.Singularity_local/` to your `.gitignore` to avoid committing database information.

## Git integration using Docker on Mac

If using Docker Desktop for Mac, ensure that your VM settings use **gRPC FUSE** instead of **VirtioFS**. There is currently a known bug with VirtioFS that prevents proper branch detection and live updates inside containers.
